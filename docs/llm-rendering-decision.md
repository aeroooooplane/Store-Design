# 不自备GPU的大模型设计路线：可行性与取舍

核对日期：2026-09-23。本文是方案分析，尚未把云端模型API接入Demo，也没有执行新的收费图片请求。

## 决策建议

建议把主路线改为：案例检索＋大模型生成结构化布局＋程序建模/校验＋统一场景多机位渲染，必要时以图像模型增强视觉。无需以训练自有模型为前提，也无需购买NVIDIA显卡。云模型仍消耗服务商算力；本地Three.js预览会使用现有集成显卡，不等于整个链路物理上不使用GPU。

如果产品只要求展示概念，大模型直接生成参考效果图可作为快速模式。如果要求平面、白膜、8张图、物料清单互相对应，则必须保存统一、可计算的空间模型。用户仍可只输入条件、选择方案，其余由系统自动完成；引擎存在不意味着用户要手动建模。

## “让模型学习”的三种含义

1. 提供案例和规则作为上下文：现在就可做。将已核验的图纸提炼为规则、参数、参考图，每次生成时按铺型/面积/空间形状选取相关案例。规则保存在项目文件或数据库，不依赖对话永久记忆。这不会修改大模型权重。
2. 更新案例库：用户修改后保存具体修改、适用条件与是否经确认，供后续检索；不要自动把每次个人偏好写成品牌标准。系统表现可随数据整理改善，但不应宣传为自动完成参数训练。
3. 真正微调模型权重：不能通过这个聊天会话直接修改当前助手。云训练在服务支持时可省去自备GPU，但需要专门训练服务、数据与预算。当前OpenAI文档说明微调平台正收缩，新用户无法进入；且视觉微调改善的是图像理解，不是用效果图训练图像输出。因此本项目不应把“直接微调当前助手成为影石渲染器”作为依赖。[官方视觉微调文档](https://developers.openai.com/api/docs/guides/vision-fine-tuning)

官方优化指南也支持先提供相关上下文、示例并评估，再判断是否需要微调；不是每个定制应用都必须先训练。[官方模型优化指南](https://developers.openai.com/api/docs/guides/model-optimization)

## 能力逐环节判断

| 环节 | 可实现方式 | 需要保留的边界 |
|---|---|---|
| 阅读历史门店 | 大模型分析平面/效果图，提取物件与关系，记录页码和置信度 | 扫描图、尺寸基准、版本需核验；看图不是精确CAD解析 |
| 生成4个平面 | 输出同一JSON规范的物件与位置，程序检查边界/重叠/入口等 | JSON格式正确不等于空间合理；失败必须回传修正 |
| 生成3D白膜 | 根据同一份尺寸、坐标、朝向、高度和模型引用，用Three.js/建模脚本实例化 | 大模型生成一张白色空间图片，不等于获得可旋转可测量的3D模型；缺失高度需明确默认或待补 |
| SI风格图 | 使用风格参考图和对应机位白膜图作为图像模型输入 | 可以做视觉方案；不能保证不移动道具、不改门头、不增加物件 |
| 8个角度 | 同一3D场景设定8个固定相机，再渲染或逐张受参考图引导增强 | 八次独立生图、多视图拼图或相同提示词均不是三维一致性保证 |
| 物料和PDF | 从布局/场景对象ID、型号、数量生成清单和图纸，打包经确认的图 | 不从生图结果反推物料；若生图有增减，与清单发生冲突需重做或标记未验收 |

官方图像API支持参考图编辑和多轮图像工作流，但明确列出跨次生成一致性、文字和精确构图方面的限制。将其应用到门店8视角时，几何漂移风险是基于这些能力边界作出的工程判断，不是本项目已完成对比实验的结论。[官方图像生成文档](https://developers.openai.com/api/docs/guides/image-generation)

## 哪条路线好

| 路线 | 本地NVIDIA需求 | 视觉表现潜力 | 几何与物料一致性 | 本项目定位 |
|---|---|---|---|---|
| 全部直接生图 | 无，使用云图像服务 | 能快速探索风格，需实测品牌还原 | 弱，尺寸和隐藏面无法保证 | 概念草案 |
| 大模型＋真实3D＋可选生图增强 | 无专用训练卡要求；预览用集显，重渲染可CPU或云端 | 取决于资产/材质/光照与增强质量 | 3D原始渲染强；增强图仍需复核 | 推荐主路线 |
| 自训布局网络＋风格LoRA | 小模型可CPU；实用图像训练通常需要更强算力或云训练 | 依赖足够的优质数据，不保证优于现成模型 | 风格微调本身不解决3D一致性 | 数据成熟后的可选优化 |

若“最终渲染”必须与真实摆位严格一致，最终交付图应优先来自固定场景的材质/灯光渲染。AI可以帮忙选择材质、布光、生成贴图；对最终像素直接重绘的结果属于额外版本，必须经过几何与品牌审核。若用户接受概念图级别，则可直接交付经确认的AI增强图，并标明其性质。

## 推荐的数据流

输入尺寸＋铺型＋固定条件 → 检索同类案例 → 大模型输出4个布局JSON → 几何检查和自动修正 → 用户调整 → 锁定布局版本 → 实例化统一3D白膜 → 用户选择SI → 应用材质/灯光 → 同场景8机位 → 可选AI增强与对照检查 → 从同一布局生成物料清单和PDF。

每个分支保存：布局版本、引用案例、规则版本、道具型号、变换矩阵、材质方案、相机参数、模型调用版本和输出图。SI变化通常只改材质及已建模的形象构件；若不同SI要求道具尺寸/数量改变，必须产生新的布局或几何版本，不能仅靠渲染偷偷修改。

## 第一轮验证而非继续小模型训练

选一家平面和效果图明确、主要尺寸可校准的门店，留出它的布局作为答案；大模型只读取其他门店案例与新店条件。先评估生成平面边界、重叠、道具规格，再建立白膜。为比较渲染路线，可另外用该店已确认白膜，针对两种SI各做两个机位：一份3D原图，一份AI增强，检查道具数量、位置、门头、标识、配件柜与柱体是否发生变化。条件不足或图纸SI版本有疑问时标为不可评分，不得自动算通过。

先验证2个机位再扩到8个，记录通过率、人工修正次数、响应时长和每个被接受方案的总成本（包含失败重试），不提前承诺生成效果或报价。

## 对上一轮工作的调整

案例标签、来源追溯、裁切图库、训练/验证按店切分仍可复用。数量回归只是小基线，tiny LoRA只证明管线可跑，不能代表布局能力或SI渲染质量。建议保留实验记录，但暂不追加tiny训练，把精力转向大模型案例调用、真实资产、可验证的场景结构和对比实验。

当前聊天可以协助设计、写代码并调用可用图像工具；正式网页自动运行需要后端模型服务连接、凭据管理、任务队列及调用成本记录。会话中的工具可用不等于网页已经接好了API。
