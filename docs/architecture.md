# 架构说明

更新：2026-10-10。第一期已实现：shared、database；api 的项目、模型目录与文件、历史节点、共享草稿、视角、渲染图、项目导入导出、排布生成与校验；web 的项目列表（含导入导出）、设置页（AI 模型与额度）与项目工作台（历史树、多边形空间录入、三种方案生成与选用、平面编辑与草稿自动保存、三维白模与三维拖拽、白模视角、浏览器渲染、双 PDF 交付）。需求见 [requirements.md](requirements.md)，数据表见 [data-model.md](data-model.md)。重构前的实际架构见 [归档](archive/20261009-before-refactor/architecture.md)。

## 1. 总体结构

```text
浏览器 apps/web ──REST/JSON──▶ apps/api ──▶ PostgreSQL
  React + Three.js              Fastify          （database/ 管理 schema 与迁移）
  只通过 API 访问数据            │
                                ├──▶ 文件存储（STORAGE_ROOT，默认指向 资源库/ 与 data/files/）
                                ├──▶ 任务队列（jobs 表）──▶ services/worker（Python：识别、PDF、Blender）
                                └──▶ 外部大模型（DeepSeek / 通义千问 / 可选境外），密钥仅在后端
```

浏览器不连接数据库，也不持有任何密钥。三维白模与预览渲染在浏览器中执行（这是可视化，不是业务逻辑）；渲染结果上传到后端保存。

## 2. 目录与模块边界

```text
apps/
  web/                React 前端
    src/app/          路由、布局壳、Provider
    src/api/          由 OpenAPI 生成的类型和请求客户端（唯一的数据通道）
    src/features/     projects / workbench（历史树、空间录入、方案生成、平面编辑）/
                      viewer-3d / cameras / renders / delivery / recognition / agent /
                      assets / settings
    src/components/   通用 UI
    src/styles/       沿用 tokens.css 的瑞士风格
  api/                Fastify 后端
    src/config/       环境变量（zod 校验，启动时失败即退出）
    src/plugins/      db、错误处理、安全头、限流、OpenAPI、存储、请求 ID
    src/modules/<领域>/  routes.ts / service.ts / repository.ts / schemas.ts / *.test.ts
    src/ai/           模型适配层、价格表、预算账本
packages/
  shared/             前后端共享：zod 校验规则、类型、纯函数领域逻辑
    src/schemas/      Space、Layout、Item、Camera、Project 导入导出、API DTO
    src/geometry/     多边形运算、碰撞、包含、间距
    src/planner/      4 策略自动排布、软硬约束、让步记录
    src/assets/       资产契约（刚体变换、禁止镜像拉伸、正面方向）
database/             Drizzle schema、SQL 迁移、种子与目录导入脚本
services/
  worker/             Python 任务执行器：本地识别（OCR+OpenCV）、PDF 合成、后期 Blender
docs/                 本文档、需求、数据模型、API 说明、ADR
legacy/demo/          旧版，功能对齐前并行保留
tools/  资源库/        原样保留；资源库 由 API 通过白名单读取
```

**依赖方向**：`web → shared`，`api → shared + database`，`database → shared`（仅类型）。`shared` 不依赖任何运行环境（无 DOM、无 Node API），保证前端即时校验与后端权威校验使用同一份代码。

`services/worker` 使用 Python，因为 PaddleOCR、OpenCV、Blender 只有 Python 生态成熟。它不直接对外提供接口，只从 `jobs` 表领取任务、写回结果。

## 4. 关键数据流

### 4.1 生成布局
1. 前端提交空间（或引用根节点）与参数 → `POST /layouts/generate`。
2. 后端用 `packages/shared/src/planner` 生成方案（尽量多放 / 按面积推荐 / 尽量少放；“参照相似门店”待清洗数据），每个方案附校验结果与让步说明；不落库。算法：识别可靠墙的轴向边，离主入口最远的为后墙；收银台靠后墙转角；后墙预留配件柜带；中岛桌在避开入口缓冲与主通道的区域按两个朝向试排（尽量多放取全部可行位置，其余策略取最均匀的若干个）；最后沿墙放配件柜并与中岛桌保持通道。旋转约定与旧版一致（90° 时正面 +Z 转向 −X）。
3. 用户选中一个 → `POST /projects/:id/nodes` 创建 plan 节点，后端再次校验。

### 4.2 编辑与白模
平面编辑或三维拖拽都修改同一份 Layout（草稿）。前端每次操作调用 `shared` 做即时校验；保存时后端权威校验。确认后创建 white 节点，后端生成默认 8 个相机。

网页工作台（`apps/web/src/features/workbench`）的草稿规则：停止操作 800 ms 后自动保存到项目唯一的共享草稿，同一时间只发一个请求，保存途中的修改留待下一次保存；版本冲突时停止自动保存，由用户载入最新草稿。草稿属于其他节点时，当前节点只读，需先“转到草稿”或丢弃草稿。“保存为新版本”创建 edit 节点，“确认白模”创建 white 节点（存在错误时不可确认），成功后删除草稿。选中的节点记录在地址栏 `?node=`，刷新后保持。

三维白模（`apps/web/src/features/viewer3d`，Three.js）与平面共用同一份布局：在三维中拖动道具即在地面平面上移动（10 mm 吸附），平面与三维随时切换。场景由 `packages/shared/src/scene` 的确定性几何生成：地面为空间多边形；入口与开放边不建墙；背向入口的墙为全高，其余墙截到 0.7 m 以便看清室内（与旧版一致）；中岛店不建墙；障碍物按多边形拉伸。模型按底部中心放在道具中心，旋转与旧版一致（90° 时正面 +Z 转向 −X），缺失或加载失败的模型以带轮廓的方框代替并提示。白模材质一律为哑光白：透明度 ≥ 0.4 的面板按实体显示，低于 0.4 的玻璃保持半透明且不投影；双面绘制并用平面着色，避免 SketchUp 导出的反面与反向法线造成破洞和发黑。视角缩略图用同一场景、同一渲染器按视角相机渲染，逐张渲染不阻塞页面。

浏览器渲染（渲染节点，`RenderStage`）：每个视角渲染一张白模图和一张材质图（1800×1200，3:2），两者是同一场景、同一相机、同样的物体显隐，只切换材质（`WhiteScene.setLook`）。材质外观按《店铺形象设计标准》SI1.0/SI2.0 手册（`资源库/05_店铺形象设计标准`，手册只给材料与规格，颜色取自其样板照片），数值与页码集中在 `viewer3d/render-look.ts` 的 `RENDER_LOOK`：SI1.0 边厅为 800×800 浅灰柔光砖、白色微水泥墙；SI2.0 边厅为 1200×600 浅灰白仿水磨石（长边平行主入口）、星空灰铝塑板墙；边厅地砖自主入口中线排起；中岛店不论 SI 都用 600×300 浅灰锁扣地板（沿店铺长边错缝），沿真实轮廓加 80 mm 银灰哑光不锈钢包边；道具使用模型库原始 `model.glb` 的材质与贴图（只在材质图需要时加载），按材质名调整光泽（不锈钢/金属、烤漆/人造石、玻璃/亚克力、画面/屏幕自发光）。打开渲染节点时自动补渲缺少的图；图片逐张上传，服务端按节点当前的空间、布局、SI、市场与所用模型文件计算布局签名，按视角位置、目标与视野计算视角签名，签名变化后旧图标记“过期”（改视角名称不算），重新渲染即更新；下载只打包未过期的图。灯箱画面与品牌 Logo 尚未接入渲染。

历史按阶段分层（用户 2026-10-10 确认）：项目 → 空间 → 方案 → 白模 → 渲染，各阶段固定在自己的层级。服务端强制：方案只能建在空间下、白模只能建在方案下（旧版本的“编辑”节点视为方案层）、渲染只能建在白模下。阶段内的修改只存在共享草稿中，不会往下加层；“新建副本”在同一层另存（父节点为该阶段的上一层，旧项目中嵌套过深的节点复制后回到正确层级，`sourceNodeId` 让白模副本沿用原白模的视角），“确认白模”“开始渲染”用当前（含草稿）的布局在下一层新建节点，原节点不变。生成方案一次保存三个方案，再次生成新增一组（编号区分）。渲染节点沿用其白模的视角。各阶段面板：方案与白模为“新建副本｜丢弃草稿”一行、“确认白模 / 开始渲染”一行；渲染阶段为“重新渲染｜下载图片 / 生成交付文件”（交付待下一模块接入）。

历史树（`HistoryTree`）画成自上而下的树状图，位于左栏、可收起：根节点为项目（深棕），一级为空间（深绿），其下的方案、编辑、白模为浅黄绿；父节点底部以细的深灰平滑曲线分叉、箭头指向子节点顶部，正中的子节点为直线；相邻叶节点上下错落。节点可拖动（按下不移动即为打开该节点），连线跟随；拖动后的位置按项目记在本浏览器（localStorage），“重置位置”恢复自动排列；“放大”在页面上方铺开查看，Esc 还原。不再画虚线椭圆（用户 2026-10-10）。布局为整齐树（子树按需占宽、居中、连线不交叉），样式全部集中在 `tree-layout.ts` 的 `TREE_STYLE`（方向、颜色、尺寸、间距、曲线、箭头、拖动阈值），以后调整格式只改这一处。

平面图（`PlanView`）按门店图纸样式绘制：墙体为边界外侧的斜交叉填充墙带（与三维白模同一组墙段，转角斜接，入口与开放边断开，中岛店不画墙），边界画红色租赁线，柱子同样填充；每条边外侧有尺寸链（在入口与开放边端点处分段，单位毫米）；道具用品类图库的 SVG 平面图按真实尺寸绘制并按模型正面方向与道具旋转对齐，没有平面图的画成方块（占位为虚线带叉）；标注名称与 H 高度；左下角标注面积与层高。SVG 符号以内联方式绘制以保持线宽，载入时只保留基本图形与绘图属性，不保留脚本、链接、样式或事件属性。

工作台布局（用户 2026-10-10 草图）：三栏。左栏为项目卡片（名称、铺位与市场、面积尺寸层高、SI 切换）、历史树、常驻的“添加模型”列表（缩略图、名称、尺寸）；中栏为节点名称、平面｜三维切换与撤回重做、主画布，另一视图以缩略图显示在画布右下角，点击即切换（平面与三维始终同时加载）；右栏为阶段面板、选中道具（尺寸、水平与垂直位置、正反两向旋转、删除）、检查、白模视角。空间、渲染、草稿占用等页面使用同一三栏框架（`WorkbenchLayout`）。整体样式改为柔和配色与圆角（`tokens.css` 的 --accent、--radius 等）。

编辑：撤回 / 重做（工具栏弧形箭头，Ctrl+Z、Ctrl+Y 或 Ctrl+Shift+Z，输入框内不拦截），每次编辑会话最多 100 步，一次拖动或连续的方向键微调算一步。平面与三维拖动带磁吸：道具边缘距轴向墙面或相邻道具边缘 100 mm 以内自动贴靠或对齐，吸附的轴保留毫米精度（不再按 10 mm 取整），按住 Alt 临时关闭。

添加模型：按项目 SI 风格列出软装道具，信息化物料、品牌标识、非标陈列两种风格都列出，环境设施不列出；卡片显示品类图库中的效果图（缺少时显示 SketchUp 预览并标注）。没有网页模型的模型以真实尺寸的占位方框加入（平面与三维），有网页模型后无需改布局即可显示真实模型。项目页顶部可随时切换 SI 风格，只影响之后的自动排布和添加模型。挂墙类（广告机、LOGO 等）目前仍从地面起算高度，待增加安装高度后修正。

三维加载性能：原始网页模型多达 250 万面、35 MB，白模加载其轻量版（`网页模型/<资产>/white.glb`，全部 38 件合计约 3 MB）；每件模型的不透明部件与玻璃部件分别合并为一个网格并共用材质，一件道具只需一两次绘制；GLB 在 Web Worker 中解码；阴影只在场景内容变化时重算；三维代码在用户停留在平面时预先加载。

### 4.3 渲染
浏览器按节点的相机列表渲染白模图与材质图（同一场景、同一相机，只切换材质），逐张上传。后端记录布局签名与相机签名；布局或相机变化后旧图标记为过期，不覆盖。

### 4.4 交付
渲染节点点“生成交付文件”（所有视角的白模图与材质图都已渲染且未过期才可用）：浏览器按《店铺形象设计标准》的平面样式把节点布局画成编号平面（黄色编号 01、02…，与图例同一编号规则 `deliveryLegend`，另有主客流方向箭头），导出 4000 px 宽的 PNG 与独立 SVG 一并提交；API 直接生成（第一期不经 worker，数秒完成）：

- `00-影石xxx店完整方案.pdf`（A3 横版）：平面页（编号平面、图例、概况、设计说明与校核：让步项、检查提示、占位说明、渲染说明）、效果图总览、每个材质视角一页、白模与校核总览。
- `影石xxx店方案.pdf`：首页只有店名、平面与图例；之后每页一张材质图（保持原始比例，视角标题与页码），不含总览、白模与文字页。
- 店名为“影石”+项目名+“店”，不重复追加；文字用随附的思源黑体子集（`apps/api/assets/fonts`，SIL OFL）。效果图在 PDF 中转为 JPEG，归档保留原始 PNG。
- 交付目录 `门店名称_门店类型_面积_日期`（同名追加 `_修订02`…，不覆盖）：两份 PDF、`01_平面图`（PNG、SVG）、`02_效果图`（材质图）、`03_总览`（白模图）、`04_源文件与记录`（项目 JSON、交付记录 JSON：页序、视角映射、图片哈希、布局签名）。目录写入 `ARCHIVE_ROOT`，并打包 ZIP 存入 `data/files` 供下载；`deliveries` 表记录文件与清单。

### 4.5 识别（第二期）
已实现（2026-10-12）。本机与 CI 没有 Python / OpenCV / OCR，而示例简图的尺寸都来自文字，因此“本地识别”定为：浏览器用 pdf.js 直接读出**矢量 PDF** 页面的文字、线段、矩形与颜色（`apps/web/src/features/recognition/pdf-extract.ts`；pdf.js 5 把路径打包在 `constructPath` 里，绘制动作与路径同在一条操作中），服务端做几何推断（`apps/api/src/modules/recognition/local.ts`）：边界取“完整包含多数道具框的最小闭合矩形”（异形店找不到就留空让用户画）；比例由尺寸标注、带尺寸的道具名称（“1.8米中岛桌”与它的图框）、“店铺实测面积 31.5m²”与边界面积三类依据一起聚类，取相互一致最多的一簇，两处以上一致才算核对过；道具文字按名称/尺寸对应模型库（`check.ts` 的 `matchCatalog`），道具框从线段重建（CAD 导出的框是四条线而非矩形），红色为新增需求，边界外为区域外；“主入口/主人流通道”文字决定入口所在边。实测发现 CAD 导出 PDF 的尺寸数字多为曲线而非文字，所以比例主要靠道具名称与面积；没有写尺寸的道具名（“边桌配件柜”）在模型库只有一种尺寸时也能作依据；“店铺实测面积：31.5m²”常被拆成几段文字，按同一行合并。边界先找四边闭合的矩形，找不到装着道具的再放宽为“三边闭合、前边可全开（租赁线虚线）、开口边不沿道具框”；梯形、扇形等异形店返回空边界，提示“比例与道具已识别，请手动绘制边界”。回归：`apps/web` 下 `node src/scripts/local-regression.ts <图纸目录> --limit 15 --pages 6`（Node 直接运行 pdf.js 与本地引擎，不经浏览器和 API）；2026-10-12 对 资源库/01_各门店原图纸 前 15 份：14 个平面页成功 10，其余 2 页为异形店（正确留空）、2 页为局部大样（面积不合理，正确失败），道具对应率 74%。JPG/PNG 与扫描件本地读不出文字，直接走所选的视觉模型（`llm.ts`：中文提示词、像素坐标、严格 JSON，图片缩到长边 2000 px 后发送，结果按比例还原），同样经 `check.ts` 校验。失败判定按需求 4.2，自动改用“识别失败后”的模型，两次记录都保留。前端 `RecognitionPanel`：选文件 → PDF 选页（缩略图）→ 图上框选区域 / 指定已知长度 → 识别 → 结果叠加在图上，待确认事项与道具表（可改型号）→ 复用 `SpaceEditor` 校对 → 确认生成 `origin = recognition` 的空间节点（`origin_ref` 指向识别记录）。

### 4.6 Agent（第三期）
后端已实现（2026-10-12，`apps/api/src/modules/agent/`）。前端发送消息（可附当前节点、选中道具与平面截图）→ api 把项目状态摘要（空间尺寸、入口、障碍物、当前节点、道具表、检查问题，单位毫米）放进系统提示并调用模型 → 模型请求工具 → api 执行工具 → 工具结果回传模型，最多 8 轮，模型给出文字回答后一次性返回（未做流式）。工具（`tools.ts`）复用各模块的 service，与人工操作走同一校验：查看状态、列模型（按项目 SI 风格）、生成三方案、放置/移动/旋转/删除道具、检查、切换风格与市场、确认白模、创建渲染节点、导出。放置用"靠哪面墙 + 沿墙 0–1 位置"描述，坐标、朝向（规划器的 `rotationFacing`：正面朝店内，无正面则长边沿墙）和占地由程序算；每次修改在当前节点的同一阶段生成 `origin = agent` 的新节点（空间下建方案；方案或白模旁另存"… · Agent"），后续工具在新节点上继续。模型调用层 `ai/chat.ts` 统一支持工具调用（OpenAI 兼容格式的 tools/tool_calls 与 Claude 的 tool_use/tool_result）。对话、每轮模型消息、工具结果与动作（`agent_sessions` / `agent_messages` / `agent_actions`）按项目长期保存；撤销一次动作即隐藏它生成的节点（生成三方案时隐藏三个），只读工具和改项目设置的动作不可撤销。回放历史时只带用户与助理的文字，不带工具往返，避免跨厂商的格式差异。没有配置任何可用模型时发消息返回 400；模型失败（502）或超额（402）时用户消息仍保留。

前端（`apps/web/src/features/agent/`）：工作台右下角的"设计助理"按钮展开为对话面板（`AgentDock`），所有阶段都可用；发送时带当前节点、平面上选中的道具（`PlanEditor` 通过 `AgentSelectionContext` 上报）和当前平面 SVG 导出的 PNG 截图（可取消勾选）；回复下列出每次工具动作（成功/失败、"查看"切到生成的节点、"撤销"），收到 `currentNodeId` 后自动切换到助理生成的节点并刷新历史树。第一句话才创建对话，标题取自第一句；头部可切换项目的历史对话或开新对话。没有可用模型时面板提示去设置页配置密钥并禁用输入。

## 5. AI 适配层

- 接口：`chat(messages, tools, images)`，各厂商实现一个适配器；DeepSeek 与通义千问均使用其官方兼容接口。
- 模型清单与单价放在 `apps/api/src/ai/models.json`（随代码版本管理，价格变化时修改）；密钥来自环境变量。未配置密钥或未开启开关的模型不出现在前端列表。
- 每次调用前检查当日预算余额，调用后按实际 token 记账；超额返回 `402 BUDGET_EXCEEDED`。已实现：`apps/api/src/ai/`（models.ts 清单与估算单价、budget.ts 北京时间日账本、settings.ts 全站设置与默认选择、chat.ts 统一调用）；设置页 `/settings`。密钥为空的厂商不出现；境外模型由 `ENABLE_OVERSEAS_MODELS` 控制。

## 6. 安全

- CORS 只放行前端来源；安全响应头；生产环境不返回堆栈。
- 请求体：JSON 5MB；上传 20MB；渲染图单张 10MB。
- 写接口与 AI 接口限流。
- 文件只能按登记过的 ID 读取，路径经过 realpath 校验，不能越出存储根目录（沿用旧版白名单做法）。
- 目录数据（模型库、门店资料、SI 标准）无写接口，只能命令行导入。
- 当前无登录，所有接口公开；这是开发期的已知限制，部署前必须加入用户系统（见需求第 13 节）。

## 8. 技术决定

| 决定 | 理由 |
|---|---|
| Fastify + zod + fastify-type-provider-zod | 校验规则与 OpenAPI 同源，减少重复定义 |
| Drizzle | SQL 优先，迁移为可读 SQL，放在 `database/` |
| 布局存 JSONB，不拆道具表 | 历史快照不可变、整体读写、兼容旧项目 JSON；以后需要统计再加派生表 |
| 渲染在浏览器 | 无需 GPU 服务器即可上线；Blender 在第四期作为 worker 任务加入 |
| 任务队列用 PostgreSQL 表 | 3 人规模不需要 Redis；`SELECT … FOR UPDATE SKIP LOCKED` 领取任务 |
| Python worker 独立 | OCR、OpenCV、Blender 依赖 Python；与 Node 服务解耦 |
| PDF 由 worker 用无头 Chromium 将 HTML 打印为 PDF | 中文排版可控，两份 PDF 共用同一模板与图片 |
| Node 24 直接运行 TypeScript（类型擦除），不设构建步骤 | 后端与脚本无需编译产物；`tsc` 只做类型检查。代码限定为可擦除语法（`erasableSyntaxOnly`），导入写 `.ts` 扩展名 |
| 开发与测试默认使用 PGlite | 本机未安装 PostgreSQL 也能开发；PGlite 是编译为 WebAssembly 的 PostgreSQL 17，迁移文件与正式库完全相同。部署时 `DATABASE_URL` 改为 `postgres://` |
| TypeScript 固定 6.0.x | typescript-eslint 8 尚不支持 TypeScript 7 |

## 9. 用户系统扩展点

当前不做登录，但以下位置已为接入用户系统预留，接入时不需要改动业务模块的函数签名：

| 位置 | 现在 | 接入后 |
|---|---|---|
| `apps/api/src/context/actor.ts` 的 `resolveActor` | 每个请求都是 `{ kind: 'visitor' }` | 校验会话或令牌，返回 `{ kind: 'user', userId }` |
| `apps/api/src/context/policy.ts` 的 `authorize` | 全部放行 | 按项目归属判断，不满足时抛 `FORBIDDEN` |
| 服务层 | 每个服务函数接收 `RequestContext`，读写前先调用 `authorize` | 不变 |
| `audit_events.actor_kind` | 记录 `visitor` | 记录 `user`，并通过迁移增加操作人字段 |
| `projects` 表 | 无归属字段 | 迁移增加归属字段并回填 |
| `app_settings` | 全站设置 | 新增 `user_settings` 覆盖全站默认值 |

请求体使用严格校验（拒绝未知字段），因此客户端无法自行传入归属或用户编号。
